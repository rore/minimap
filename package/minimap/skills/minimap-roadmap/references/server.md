# Server Lifecycle

Use the bundled scripts only. The skill is self-contained; the scripts handle every state correctly across platforms (Windows signal limitations, TIME_WAIT, race-against-another-launcher, stale registry).

## Local trust boundary

The server binds to IPv4 loopback (`127.0.0.1`) only. Every API request must come from a loopback peer and carry a loopback `Host`; when a browser supplies `Origin`, it must exactly match that request origin. Foreign origins are rejected before route work, while origin-less local CLI and lifecycle requests remain supported.

## Optional persistent service

Install once per user to keep both modes available independently of agent applications. This is separate from installing the skills: a project-local Roadmap skill and personal Spec Review skill can use the same service.

| Command | Purpose |
| --- | --- |
| `node <skill>/scripts/service.mjs install` | Copy this skill's runtime to a stable location and register/start a per-user service. |
| `node <skill>/scripts/service.mjs status` | Inspect the managed installation. |
| `node <skill>/scripts/service.mjs update` | Stage this skill's runtime, retaining the previous runtime for recovery. |
| `node <skill>/scripts/service.mjs rollback` | Restore the previous runtime. |
| `node <skill>/scripts/service.mjs uninstall` | Remove owned service registration/runtime; keep review records and settings. |

Use `MINIMAP_HOME` consistently across both skills and service commands. Installation uses `PORT` (default 4312) and the current Node executable; it does not install Node or change PATH. The stable runtime lives under `$MINIMAP_HOME/service`. Updating a skill folder alone does not update this runtime. Updates and rollback preserve the prior running/stopped state. Windows service paths cannot contain a literal `%`, because Windows Script Host expands environment references; installation rejects these paths rather than changing their meaning.

Windows uses a hidden login Scheduled Task under the ordinary user account. Linux requires a working user systemd manager. Startup is after login, not before login; the installer does not enable lingering. Native failure recovery is bounded. A deliberate stop suppresses recovery; explicit start resumes it.

Existing start/stop/restart/status commands route to this installation when configured. Managed restart uses the installed runtime; `--replace-runtime` is not a way to replace it. Use the explicit update command. Managed startup keeps its configured port rather than silently moving to another port. A foreign process or inconsistent installation produces an error; it does not authorize killing a process or falling back to another runtime.

Copying or linking a refreshed skill updates its own files; it does not deploy them to the installed service. Deploy with `node <new-skill>/scripts/service.mjs update`: the invoking skill supplies the new runtime. Older skill copies can reuse a compatible healthy server, but do not understand managed ownership; refresh them before using lifecycle commands against the service.

Installation, update, rollback and removal affect every board/spec tab using this service. Obtain explicit environment-change approval, preserve the current data directory, and verify readiness and settings after the operation. Never install a service just to satisfy a request to show a board. Tests must use isolated homes/ports; native registration tests need a separately isolated environment. On hosts without supported service management, retain standalone mode.

### Migrate from a standalone server

1. Obtain approval for the migration and use a current skill copy under the same user account. Explicitly set `MINIMAP_HOME` to the existing data directory for every command. Defaults are `%LOCALAPPDATA%\minimap` on Windows (`%USERPROFILE%\AppData\Local\minimap` if `LOCALAPPDATA` is absent) and `~/.minimap` on Linux. Back up the home, including review records and settings, while clients are idle.
2. Run `node <skill>/scripts/status.mjs`; inspect the live PID/source and coordinate with shared clients before `node <skill>/scripts/stop-server.mjs`. If ownership cannot be verified, stop and investigate rather than stopping an uncertain process.
3. Set `PORT` to the intended existing port (default 4312) and run `node <skill>/scripts/service.mjs install`. Keep the same explicit home. A pinned-port conflict is a refusal; never kill its owner, change ports silently or edit the registry to bypass it.
4. Run `node <skill>/scripts/status.mjs` and verify the live source is under that home's service directory, the port matches, and participant settings are preserved. Open its printed URL. Retain the backup until normal use is verified.

Native Windows installation and explicit restart have been verified. Login/crash recovery and native Linux supervision remain unqualified; mocked lifecycle tests do not establish those results.

## Standalone lifecycle commands

| Command | Exit codes | What it does |
| --- | --- | --- |
| `node <skill>/scripts/start-server.cjs` | 0 = running (started or reused); 1 = incompatible/unknown API, settings mismatch, or occupied port | Probe the registry and live `/health`; reuse only a compatible API with matching participant settings. |
| `node <skill>/scripts/status.mjs` | 0 = running; 1 = stale registry; 3 = not running | Print live identity, registry port/startedAt, and local lifecycle log path/recent evidence, including when stale or stopped. Legacy identity prints unknown. |
| `node <skill>/scripts/stop-server.mjs` | 0 = stopped (or was already not running, or stale cleaned); 1 = shutdown failed | `POST /api/shutdown`, wait for the port to free. |
| `node <skill>/scripts/restart-server.mjs [--replace-runtime]` | 0 = restarted; 1 = refusal, stop, start, or verification failure | Preflight registered/requested targets before any stop; default permits only the same runtime. Serialize per home, then stop/spawn and verify the child-reported port/identity/configuration. Failed cleanup targets only its own child PID. |

Exit codes follow `systemctl` conventions for `status` (0/1/3 = running/stale/not-running).

The canonical `start-server.cjs` bootstrap sets a process-local `UV_THREADPOOL_SIZE=8` only when that variable is absent, then imports the existing launcher in the same process. Restart applies the same absent-only default to its new child's environment before Node starts. Explicit values, including an empty value, are preserved. Reusing a running server does not change its pool. No persistent environment setting is written.

Legacy `start-server.mjs` remains supported without the bootstrap default, as do direct development entrypoints. Caller preloads that initialize libuv before the bootstrap must set their desired pool in the initial environment; an initialized pool cannot be retuned by the bootstrap.

## Local lifecycle diagnostics

The common server entry records startup identity (PID/parent PID, runtime source/version, port and known launch mode), graceful shutdown reasons, observed exit codes, and sanitized startup/cleanup/fatal errors under the resolved `$MINIMAP_HOME`. Foreground starts and detached restarts use the same logger. `server-lifecycle.jsonl` rotates at 128 KiB to one backup, `server-lifecycle.jsonl.1`, with a 4 KiB event limit. `status.mjs` shows the path and the last eight retained events without changing its exit codes.

These local records contain no request bodies, roadmap/spec content, environment dump, raw stderr or arbitrary error messages. Error evidence retains only recognized native class/code and up to five runtime-relative JavaScript source locations. Message detail is deliberately lost to avoid storing private content or credentials. The fatal monitor is observational: errors still terminate normally and normal stderr is unchanged. Logging I/O failure cannot block startup or shutdown.

Historical events are not proof of the current failure's cause. A verified live PID does not receive a missing-exit warning. Forced termination (including Windows hard kills/job teardown) and failures before the logger loads may leave no final event; missing exit evidence means **unknown**, not a diagnosed crash. Concurrent launch races can lose rotation evidence or briefly exceed the rotation threshold. This is bounded best-effort diagnostics, not telemetry, a watchdog, or a guarantee of recovery.

## Discovery

`start-server.cjs` reads `$MINIMAP_HOME/server.json` and probes `/health`. A compatible running API is reused even when package versions or runtime sources differ. Unknown/legacy or incompatible API identity is refused without shutdown or saved preference changes. The same checks apply to a race winner on the requested port. Both skills share one registry/server across repositories.

## Standalone runtime replacement

Health reports `runtime: { version, apiCompatibility, sourcePath }` and live `pid`. API compatibility is integer 1; it changes only for incompatible server API changes, independently of package release versions.

Routine restart requires both the running version and canonical real server source path to match this launcher's bundled runtime, and the live PID/port to match this home's registry. An unregistered requested-port server requires explicit replacement even with matching runtime identity: the same copy can serve another home. Version alone cannot distinguish development checkouts or installed copies. Editing code in place at the same path/version remains routine; this is location identity, not content attestation. Separate copies require explicit replacement even when their bytes match.

If restart refuses, inspect its running/requested version and source, coordinate with anyone using the shared board/spec server, then use `node <skill>/scripts/restart-server.mjs --replace-runtime` only when replacement is intended. This flag allows a different, incompatible, older, or unknown runtime to be replaced; it is not an automatic upgrade and interrupts all clients of that server. Explicit `stop-server.mjs` remains an intentional shared shutdown, not a version upgrade shortcut.

Restart checks every registered/requested target before any shutdown, does not sweep unrelated adjacent ports, and sends the live PID guard when available. Legacy servers cannot offer the new ownership guarantees. Update each relevant installed skill folder using the existing copy-in installation method (or its checkout link); old launcher copies cannot be retroactively protected. Updating files alone does not replace a running server.

## Multi-repo

The server is repo-agnostic. Roadmap requests carry the repo chosen by the UI's `#repo=...` URL hash in `X-Minimap-Repo`, or in `X-Minimap-Repo-Encoded` for paths that cannot be sent as an ASCII HTTP header. One server can serve any number of repos at once.

The browser's **Across worktrees** board reads `GET /api/worktree-workspace` for the opened repo. Its source-specific requests use `/api/source/...` plus the returned `X-Minimap-Source-Context`; the server rechecks the live Git checkout and roadmap location, and source-bound item/board/scope writes require `expectedRevision`. Source-bound spec paths cannot escape the checkout. The UI uses `X-Minimap-Repo-Encoded` for non-ASCII paths when needed. Do not construct or reuse a source context from a guessed path, stale response, or another repo. This is a UI safety boundary, not a new agent roadmap-editing workflow: agents continue to edit only their assigned checkout's canonical files and do not automatically copy changes across worktrees.

The source menu separately reads `GET /api/worktree-sources`: this lists discovered Git checkouts without roadmap parsing, ancestry aggregation, or participant lookup. Cached choices are discovery evidence only. Opening a choice uses `GET /api/worktree-source-workspace` with that identity in `X-Minimap-Source-Context` and its repository header; the response contains `{source, workspace}` with a fresh validated roadmap binding. Subsequent item operations use the bound route family. Discovery refresh never replaces an editor's captured context or draft, and failed refresh retains last-known choices with an unavailable cue. A failed checkout open can be retried with Refresh or the current-source choice, which rediscovers before binding. Counts distinguish discovered checkouts from loaded roadmaps and participant coverage.

Aggregate identity accepts shared-ancestor ID/path continuity or an exact complete repository transition matching a historical squash integration. Matching a new item's ID/path or content alone is insufficient. The whole-change comparison includes every changed path, mode and old/new committed blob, and retains later source edits as versions; delete/re-add breaks continuity. Independently reproducing the same complete change is indistinguishable in Git and is treated as equivalent. Squash inspection traverses first-parent histories, including merges, but only a single-parent commit can establish a matching integration. It is cached and bounded to 64 commits per history, 4 MiB per Git response, and 32 history loads / 8192 raw change records per aggregate. Positive proofs connect same-ID/path versions through a chain, even when another direct comparison lacks proof; missing, malformed or capped evidence still reports partial coverage. An explicit deletion/re-add or conflicting ancestor ID inside a proven chain separates all its versions and reports identity uncertainty. Disconnected copies remain distinct.

Across additionally resolves superseded status only when clean feature-file revisions prove strict ancestry. It batches candidate path history through the existing graph/scheduler, checks stage-zero index blobs before/after bounded committed-blob reads and binds proof to exact loaded content. Unrelated HEAD commits do not determine feature recency; dirty, incomparable, missing or capped evidence retains saved status. Status filters/grouping, primary status, Done ordering and status-based unfinished/In play classification use the resolved evidence. Historical text/non-status matching, content selection, other placement, all versions and safe pinned-file editing remain unchanged. See [roadmap-contract.md](roadmap-contract.md) for user-facing semantics and the top-level contract for bounds.

## Roadmap snapshots and observations

Checkout-identity and aggregate Git reads share cooperative FIFO launch admission: at most one child starts per event-loop turn, while child execution still overlaps and lineage retains its existing eight-slot limit. This avoids a synchronous Windows process-creation burst blocking unrelated requests; it is not a universal latency guarantee. Queued cancellation never launches a child, and active reads retain their existing signal, timeout and output bounds.

Worktree-workspace also accepts the explicit `compact=1` transport option. Its `worktreeFormat: "compact-v1"` payload references source contexts through `sources` and group placements through indexes into each feature's versions. The browser API expands it back to the existing aggregate shape. The cache stores one compact representation for legacy and compact callers; omitted `compact` returns the existing expanded shape with the same snapshot identity. Repeated or unsupported flag values return 400. This changes transport size, not identity, coverage, source validation or write authorization.

Across may request `GET /api/worktree-workspace?openedOnly=1` alongside the full aggregate. The opened-only response has `provisional: true`, `partial: true`, and `coverage.pending: true`: it loads only the opened checkout, without sibling discovery, ancestry aggregation, or participant lookup. Its feature totals and In play coverage are incomplete. The full response replaces it while preserving newer selections, filters, grouping, layout and drafts. Participant counts and details remain unknown until full feature identity is resolved.

`GET /api/workspace` and `GET /api/worktree-workspace` accept `cached=1` for cached reads. Worktree-workspace also accepts `openedOnly=1` and `participants=0`; the latter skips combined participant enrichment. Unsupported or repeated query values return 400. Omitting `cached` requests fresh validation; omitting `participants` retains legacy enrichment. Responses add `snapshot: { id, validatedAt, stale, refreshing }` without changing the workspace or aggregate shape. Snapshots are scoped to the canonical opened repository and read mode, considered fresh for 30 seconds, and retained for at most five minutes, within 16 entries and 96 MiB of serialized data. Changed source or roadmap-binding admission evidence forces validation; mutable file changes enter the next validated snapshot.

The visible UI reuses a current snapshot without another scan, validates a stale snapshot, and always requests fresh validation for Manual Refresh or a tracked Spec mutation. Hiding the tab preserves an already-started bounded workspace read; new automatic reads, including stale-cache followups, wait until the tab is visible. Superseded requests and navigation to Spec still cancel that subscriber; another subscriber can keep the shared scan alive. Returning reuses a completed current snapshot or resumes needed validation while retaining the last-known view and drafts. A failed read retains explicitly stale same-scope content and drafts. HTTP 409 `snapshot_invalidated` permits one retry within the original request deadline; queue saturation or an exhausted request budget returns HTTP 503 `snapshot_unavailable`. Full Across scans have a total 60-second budget, including queue waiting; This worktree, source-open and opened-only reads retain their 30-second budgets. At most two regular scans run alongside one reserved This/source-open/opened-only scan, so two Across loads cannot occupy every scan slot. Source-bound workspace reads share one 30-second request budget across initial source validation and the workspace handler; disconnect cancels both, and validation timeout uses the same HTTP 503 `snapshot_unavailable` result. These deadlines do not change the 30-second snapshot freshness interval. Cached reads never satisfy live source or write-revision guards.

Both board modes use `GET /api/board/observations?snapshot=<id>` for independent participant observations. Send the opened repository header, not a selected sibling's source context. The opaque ID selects a retained manifest of validated references and ambiguity coverage, so observations do not rescan Git. Unfinished references precede completed references within the 200-reference cap. Observation availability and timestamps are separate from roadmap validation; failures retain prior counts as stale rather than zero. A wrong-scope, expired, evicted or invalidated ID returns HTTP 409 `snapshot_expired` and requires normal roadmap validation. Legacy `/api/board/participant-counts` remains supported. The UI adds `includeCompleted=1` only when In play can include completed statuses; ordinary observations omit completed candidates.

Feature detail independently reads `GET /api/items/<id>/related-work`. This worktree reads its selected checkout; Across composes source-bound reads from the unique checkout contexts in the full proven feature version set, independent of selected document and filters. At most four reads run concurrently, with one 20-record page per source per wave and no eager pagination. Exact task references share one row while every source version keeps its own saved state, PR links and origin-specific Open task. Matching summaries do not prove matching bodies. Across counts remain known unique references with + until every source completes successfully; incomplete coverage never proves zero. Across task caches use the complete source identity/binding/revision set for 30 seconds and reuse pending reads across document-version switches. More reveals local rows first; a source-local generation eviction removes only that source's old pages and retries page one fresh once, preserving peers and a visible changed-generation notice until the next fresh validation. Reopen caches retain the recovered first page and notice. The separate related-work snapshot cache holds up to 32 indexes within its unchanged 16 MiB/time limits. The read-only result derives exact references from the configured local Agent Workflow Work Records. It includes recorded title/state, recorded PR URLs, selected source provenance, coverage, status (`ok`, `partial`, `stale`, or `unavailable`), and at most 20 records per page. The UI labels these as tasks linked to the feature and opens them as task records. Successful participant and This worktree first-page task reads are reused for 30 seconds only within the same repository, mode, source/version, feature and item revision; pending reads in that scope are shared, including a brief overlay close/reopen. Partial results keep their coverage warning. Visible automatic refresh checks expired reads and requests `fresh=1` when server validation is due; manual Refresh forces fresh reads without delaying board, item, or draft reads. `generation=<id>&offset=<n>` continues an immutable page; same-generation automatic/manual checks and same-key cache reuse retain the pages/cursor already loaded in the current view while updating status and coverage. Reopening retains the existing first-page-only cache behavior. A changed or expired generation returns HTTP 409 `related_work_changed` and requires starting at page one. `generation=<id>&record=<work-record-ref>` opens only a record in that feature's validated index, after checking its path and content hash. Missing or unsupported Workflow metadata never creates inferred links. A failed refresh can retain a clearly stale, same-source last-good index; source/config/revision changes do not inherit that index. This endpoint creates no spec session and changes no roadmap or Work Record file.

## Optional Pallium participants

Set `MINIMAP_PALLIUM_ENDPOINT` on a supported start or restart command to enable read-only participant lookup. Set `MINIMAP_PALLIUM_DASHBOARD_ENDPOINT` separately, and only for a reviewed compatible Pallium dashboard, to enable exact-session participant links. Both values must be explicit local HTTP origins such as `http://127.0.0.1:19836`; Minimap rejects remote, credential-bearing, redirected, or path-bearing endpoints before changing a running server or its saved preference. A successful command saves the validated settings under `$MINIMAP_HOME`, so later starts and restarts preserve them. An explicit empty dashboard value disables links while retaining lookup; an explicit empty lookup value disables lookup and clears both.

If `start-server.cjs` finds a healthy server and the requested or saved effective settings do not exactly match the server's verified effective identity, or a legacy server cannot verify it, the script exits with restart guidance instead of silently reusing it. `status.mjs` reports participant lookup and participant links independently as enabled, disabled, or unknown without exposing either origin. Do not edit the private preference file by hand; use the lifecycle scripts and environment variables.

When disabled, Minimap makes no Pallium HTTP requests and all normal roadmap behavior remains available. The server setting controls only the read-only item panel: the public `minimap roadmap item-ref` command and already-available Pallium MCP work-reference tools remain independent.

## URL

```text
http://localhost:<port>/#repo=<absolute-path-to-active-repo>&view=board
```

Use the port printed by `status.mjs`. Standalone startup may fall forward from a busy default port; a managed service keeps its installed port and refuses a conflict.
