## Cache publication and freshness design gate

Manager proposal for Delivery 2b, pending technical review (not implementation acceptance):

- Keep one process-local read coordinator for the existing server. Key snapshots by canonical opened repository and read mode; record actual source identities and roadmap bindings in the value. Do not reuse one checkout's opened-first projection for another checkout. Return detached JSON data; callers must not mutate a shared cached workspace.
- Mutable snapshots are considered fresh for 30 seconds, retained for at most five minutes, with at most 16 scope entries and 64 MiB of serialized snapshot data. Oversized snapshots may be returned to current callers but are not retained. Eviction removes settled least-recently-used entries; do not evict a live job and silently start its duplicate. These are proposed bounds to validate against the acceptance fixtures.
- An explicit opt-in cached-read request may return the same scope's retained snapshot immediately with validatedAt, stale, and refreshing metadata. Existing clients retain fresh-read response semantics. A new client follows a cached read with a fresh validation request and applies the result through the existing draft-preserving reconciliation. Manual Refresh always requests validation, sharing an already-running same-generation scan; cached data must not masquerade as refreshed data.
- Visible roadmap views request validation every 30 seconds and on visibility return after expiry; hidden views stop starting work. Participant observations use the same visible/return policy in both modes but a separate batched endpoint over a known snapshot identity. No Git scan per badge tick and no wait for Pallium before returning roadmap cards. Compatibility of older combined callers must be covered explicitly rather than silently removing their participant fields.
- Start with at most two full scans across the process, one per scope, and eight queued distinct scopes. Bound each job, including queue time, to 30 seconds; excess work returns an explicit temporary unavailable result while preserving cached content. Subscriber cancellation removes only that subscriber; cancel queued/running work when none remain. Propagate abort and remaining deadline into Git/file stages; do not wait for all per-command timeouts after the job deadline.
- Every scan reads current inventory, source context, config, board, scope and item content, so uncommitted changes enter the next validated snapshot. No HEAD-only mutable cache. Successful server mutations invalidate affected scope generations before an old job can publish; for the first implementation, invalidating all retained roadmap scopes on a successful file mutation is acceptable if measurement supports it. External changes become visible at the next successful bounded validation. Read caching never substitutes for live mutation guards.
- A job publishes only into its captured generation and only after source validation. Older or invalidated jobs cannot repopulate the cache, even after eviction/recreation. Preserve last successful data on failed validation. Identity lookup unavailable is a different outcome from positively observed source movement. Retry confirmed transient movement at most once inside the same total deadline; do not stack client retries over server retries.
- Deterministic regression gates: coalescing, per-scope isolation, subscriber independence, abandoned jobs, queue saturation/deadline, eviction/byte limits, dirty/add/delete/config/inventory changes, external source replacement, invalidation during a delayed scan, source/write guard preservation, cached/fresh metadata and legacy endpoint compatibility. Measure multi-project lightweight HTTP latency under the capped scan load before accepting the numerical bounds.

Open technical question for review: whether two full scans are still too costly for synchronous parse/serialization slices at 16 x 1,000 items. Measure before introducing workers; smaller yielding batches or one scan may suffice. Keep background refresh and participant endpoint wiring in one coherent client/server delivery so no intermediate shipped state depends on an unimplemented follow-up.

Before Delivery 2b implementation, record and review explicit freshness durations, memory/entry limits, scan concurrency/budget and Manual Refresh behavior. Last-known read results may be served with age/stale metadata while revalidation runs. Manual Refresh must request new validation (and may share validation already in progress), never claim a cached response freshly validated without evidence.

Every scope has an invalidation generation. An in-flight scan captures it; publish only if that generation is still current and no newer validation has published. Successful writes and explicit invalidation advance it. Add a deterministic delayed-old-scan test proving invalidated data cannot repopulate the cache after a write or newer scan. File/config fingerprints and bounded revalidation include uncommitted changes; write-time source/revision guards always read current evidence.
