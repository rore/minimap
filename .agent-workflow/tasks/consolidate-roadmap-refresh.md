Concrete contract decisions after the first technical review (supersede ambiguous proposal wording):

1. Cached reads are an explicit `cached=1` opt-in on `/api/workspace` and `/api/worktree-workspace`. Unspecified remains a fresh validation, including legacy combined participant enrichment. `participants=0` on the latter opts the new client out of blocking provider enrichment; omitted retains legacy fields/semantics. Reject duplicate or unsupported query values. A cache miss waits for a bounded fresh scan; Across retains its existing opened-only fallback. Responses add `snapshot: { id, validatedAt, stale, refreshing }`; the actual workspace/aggregate shape is unchanged. The opaque ID binds exact opened scope, generation and published snapshot, never a client-supplied set of paths or feature keys.
2. Before cached reuse, compare inexpensive filesystem admission evidence captured by the scan for each recorded source: resolved root and Git directory locations/identities, `.git` indirection, HEAD content, roadmap config content and resolved binding. Changed evidence discards the cached snapshot and forces bounded validation; unavailable evidence cannot be reported as a valid cache hit. This check does not assert mutable item content is unchanged: the 30-second validation policy remains explicit. Worktree inventory additions are found by scheduled validation; missing/replaced known roots are rejected during admission. Do not add a second identity algorithm: reuse existing path/stat/binding primitives, leaving live Git source guards unchanged. Admission itself is abortable and inside the request's total deadline; if admission is too costly for the target, measure and revise before accepting performance.
3. Successful mutations immediately mark retained entries stale and increment a process generation before responding. Abort affected old jobs and reject their subscribers with HTTP 409 `snapshot_invalidated`, without returning the invalidated result as fresh. A new validation waits for the cancelled job to relinquish its slot before starting; callers may rejoin the one new-generation job. Check generation again immediately before sending a fresh response, not just on cache insertion. New UI retries that code once within its original deadline and otherwise retains explicit last-known content. Old clients already retain content on failed refresh. Preserve generation ordering across entry eviction with a process-level epoch, not a recreated per-entry counter.
4. Add a batched observation endpoint `/api/board/observations?snapshot=<id>&includeCompleted=1` carrying the opened repo header. It uses only the server-retained snapshot manifest (validated exact references, source keys and ambiguity/coverage), never scans Git to answer. Invalid/expired/evicted/invalidated or wrong-scope IDs return HTTP 409 `snapshot_expired`; client preserves previous observations as stale and schedules normal roadmap validation. Snapshot manifests share the 16-entry/five-minute bounds; an oversized payload may retain a bounded manifest only, not defeat the byte limit. Return participant availability and timestamps separately from roadmap validation. Disabled/unavailable/partial never mean zero. Unfinished candidates precede completed candidates within the existing 200-reference cap; ambiguity is classified before truncation. Reuse existing lifecycle/reference validation and batched provider code.
5. All full workspace reads consume the same two execution slots and eight queued distinct scope/mode jobs: This, opened-only, full Across and legacy fresh endpoints. Cached admission and manifest-only provider observations do not consume a full-scan slot. Register disconnect cancellation before any asynchronous preparation, then start one 30-second budget including repository resolution, queue, identity, scan and retries. Opened-only jobs may take the next free slot ahead of a full Across job, but after one priority admission admit the oldest regular job to prevent starvation. Do not preempt a running job. Cold two-request fallback stays within two slots; identical keys share work. Queue overflow or deadline returns HTTP 503 `snapshot_unavailable`, handled by existing last-known/setup failure paths. Provider enrichment retains its own existing timeout and never consumes a scan slot after the snapshot is ready.
6. No persistent background job is required for cached reads: the visible client owns the follow-up fresh request. This gives cancellation a real subscriber, keeps hidden tabs quiet, and avoids an independent refresh scheduler. Fresh reads may share a scan already in progress. Client abort controllers cancel superseded/hidden refresh requests; another tab's subscriber keeps shared work alive. Existing source-bound detail/mutation checks remain live and are never satisfied from the cache.

Before Delivery 2b implementation, record and review explicit freshness durations, memory/entry limits, scan concurrency/budget and Manual Refresh behavior. Last-known read results may be served with age/stale metadata while revalidation runs. Manual Refresh must request new validation (and may share validation already in progress), never claim a cached response freshly validated without evidence.

Every scope has an invalidation generation. An in-flight scan captures it; publish only if that generation is still current and no newer validation has published. Successful writes and explicit invalidation advance it. Add a deterministic delayed-old-scan test proving invalidated data cannot repopulate the cache after a write or newer scan. File/config fingerprints and bounded revalidation include uncommitted changes; write-time source/revision guards always read current evidence.
